# Pass 7C search architecture, sources, and costs

Checked against official OpenAI documentation on 2026-11-02: [Realtime function calling](https://developers.openai.com/api/docs/guides/realtime-conversations#function-calling) supports sending a local function's `function_call_output` back under the original call ID and then requesting a continuation. The [web search guide](https://developers.openai.com/api/docs/guides/tools-web-search) documents hosted `web_search` on the **Responses API**. It does not establish direct hosted web search inside this Realtime session. Therefore `search_web` is a registered read-only Realtime function whose local adapter makes one Responses API request to the fixed `https://api.openai.com/v1/responses` endpoint. No search-engine page scraping or unauthenticated site browsing is used.

The [Realtime `response.create` reference](https://platform.openai.com/docs/api-reference/realtime-client-events/response/create) documents per-response `tool_choice`, `tools`, and `output_modalities` overrides. After one search attempt in a spoken turn, the continuation now sets `tool_choice: "none"` and `output_modalities: ["audio"]`. It retains the session's tool declarations rather than overriding them with an empty array. A repeated model search request is still rejected locally without a provider call. The Pi failure at commit `3e718d7` occurred after the continuation was acknowledged but before any recorded audio or `response.done`; its `abnormal_no_frame` close had no diagnostic close code. Documentation establishes that the revised override is supported, but does not prove that the previous empty-tool override caused the closure. The cited output remains a JSON string with the original call ID and is capped at 1,800 bytes by the search adapter. Safe logs report availability, source count, and output byte count without the content. A 30-second first-audio deadline and response lifecycle logs make silent stalls bounded and distinguish them from remote closure. The existing 90-second response watchdog remains the outer limit after audio begins.

The later Pi failure at `7eb1ad5` did receive its first audio event, then closed without a close frame or `response.done` about 28 seconds later. A confirmed local bottleneck was the eight-item output queue: each item represented roughly 100 ms of speech, so a continuation arriving faster than the speaker could fill it after about 0.8 seconds. The receive loop then waited for playback and stopped reading Realtime events. The `websockets` library processes Ping/Pong in its own protocol task, but a saturated incoming frame queue can prevent that task from reading further frames; its configured 20-second Ping interval plus 10-second Pong deadline makes the hardware timing consistent with keepalive failure. The Pi log alone does **not** prove this was the particular close cause. The output queue now has a hard cap of at most 90 seconds of PCM (about 8.6 MiB at 48 kHz mono int16), with two reserved control slots. Audio enqueue never waits for playback: if the cap is exceeded, the session fails explicitly and cleans up rather than starving WebSocket reads or dropping audio silently. The receive loop yields during bursts so keepalive and speaker tasks can run. The 20/10-second keepalive settings are unchanged; increasing them would obscure this local pressure problem. When `websockets` reports its exact local `keepalive ping timeout` close, logs now classify it as `keepalive_timeout` without exposing the reason text. Safe response diagnostics include audio event count, received audio duration, and peak queue depth. A generic `abnormal_no_frame` close remains unattributed until the Pi retest.

The adapter selects [`gpt-5.4-mini`](https://developers.openai.com/api/docs/models/gpt-5.4-mini), whose model page lists Responses API web-search support. This model is separate from the configured Realtime voice model. Both calls use the existing private `OPENAI_API_KEY`; no second provider credential is needed. The search request sets `store=false`, `tool_choice=required`, `max_tool_calls=1`, low search context, and a short output cap. Only `web_search` is enabled for that Responses call. The model cannot change the endpoint, authentication header, hosted tool options, or output limits. It is instructed to prefer recent primary sources, distinguish publication date from event date, and state disagreement or insufficient evidence. The optional `freshness` argument is **guidance in the prompt**, not a guaranteed provider date filter.

The adapter accepts a provider response only if it contains a completed hosted search call and a message with `url_citation` annotations. It forwards a bounded summary, at most three cited URLs/titles, their original citation offsets into that summary, provider-supplied publisher/publication/event dates when present, a retrieval timestamp, and a `cited_not_independently_verified` confidence label. Domains are derived from validated public source URLs; publisher names and dates are left empty when absent. `action.sources` may list more URLs than are cited; uncited sources are not presented as evidence for claims. If citations are missing or the request fails, the tool returns a safe unavailable reason rather than an unsourced claim. Search text remains untrusted data; it cannot register tools or trigger actions. The dashboard renders source titles as text and their URLs as optional clickable links in the current loopback-only exchange.

Cost controls are independent of the voice session's global tool-call cap. `MIRROR_SEARCH_ENABLED=false` by default. Each active conversation allows two paid search requests by default; repeat queries within five minutes reuse its in-memory cache. A private date/count file caps searches at ten per UTC day by default, across wake-service restarts on the same Pi. Reservation occurs before sending the request; a cancelled or failed request still counts because it may be billable. The file contains no query, source, transcript, or API key. It requires a private `.private/` directory and mode-0600 file. Process restarts preserve the daily count, but a deleted file or separate installation has its own budget.

[OpenAI pricing](https://developers.openai.com/api/docs/pricing#built-in-tools), checked 2026-11-02, lists hosted web search at **$10 per 1,000 calls** ($0.01 per hosted call) plus search-content and prompt tokens at the chosen model's rates. The `gpt-5.4-mini` model page lists $0.75 per million input tokens and $4.50 per million output tokens. An **illustrative** query with one hosted search call, 3,000 total input/search-content tokens, and 200 output tokens is about **$0.013** for the Responses search portion. Actual tokens, latency, and price vary; Realtime audio usage is additional. The API's `usage` counts are forwarded as sanitized diagnostics when supplied, never raw response objects. No paid API request is made by automated tests.

Limitations: the hosted provider may omit publication dates, event dates, titles, or public citation URLs. It may surface third-party feeds without retrievable citations; this adapter declines to turn those into confirmed facts. A cited source is evidence that the provider associated a URL with text, not independent fact verification. News can be stale or contradictory. Search may time out under poor connectivity, and the Realtime model may choose not to call the optional tool even for a current question. No arbitrary site fetch, authenticated account browsing, deep research, private-network navigation, image search, or persistent search-result history is implemented.
